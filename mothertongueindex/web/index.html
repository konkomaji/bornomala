How efficient is your language on today's AI, versus English?

Every large language model reads text through a tokenizer, and every mainstream tokenizer is tuned for English. So the same sentence in another language can cost several times more tokens. That is a cost you pay, and a slice of context, and reasoning, you lose. MotherTongueIndex measures exactly how much, across 28 real model tokenizers.

Definitions

What the numbers mean

Fertility is tokens divided by whitespace words. Lower is better. It controls training cost, inference cost, and how much of your text fits in a context window.
xEN (versus English) is a model's fertility on your text divided by its fertility on English. It is the honest headline: 4.0x means four times the tokens, and roughly four times the cost, for the same kind of content on that model.
STRR, single-token retention rate, is the fraction of words the tokenizer keeps as exactly one token. It exposes vocabulary allocation that fertility alone can hide.
Bytes per token is script-independent compression: UTF-8 bytes divided by tokens. Higher is better.
Grapheme clusters per token is the true characters-per-token, counting what a reader perceives as one unit (Unicode UAX #29), not raw codepoints. For Bengali and other complex scripts this is the meaningful measure.

Beyond cost

Why tokenization hurts reasoning

A context window holds a fixed number of tokens, not a fixed amount of meaning. If your language has four times English fertility, the same window holds about a quarter of the content. Fewer few-shot examples fit. Long documents truncate sooner. Chain-of-thought has less room. The research literature links high fertility to degraded downstream performance at fixed context.

MotherTongueIndex turns that into a number: effective context ratio = English fertility divided by your language fertility, plus a risk band from low to severe. This is derived from tokenization, and labelled as such.

To measure the reasoning gap directly, the project ships a separate probe that runs the same questions in English and your language on a real model. That runs on a machine with a model or API key, by design, and never fabricates a score.

Derived vs measured. The tool is careful never to present a prediction as a measurement.
  • Derived (in the tool): effective-context loss, risk band, from the token math.
  • Measured (opt-in probe): actual accuracy on reasoning items, English versus your language.
Both belong side by side: the token overhead predicts the handicap, the probe confirms it.

Coverage

28 model tokenizers, honest tiers

Exact, no auth

OpenAI GPT-5, GPT-4o and 4.1 (o200k), GPT-4 and 3.5 (cl100k). Open weights: Qwen3, DeepSeek V3 and R1, Kimi K2, GLM-4, Yi, Phi-4, Falcon, BLOOM, XLM-R, mBERT.

Indian models

Exact, gated

Llama 4 and 3.1, Gemma 3, Mistral, Command R. Set an HF_TOKEN and accept the model owner's terms.

Estimate only

Claude, Gemini, Grok. No public tokenizer exists, so these are heuristic estimates, always labelled, never presented as measured.

Run it yourself

Command line, 30 seconds

pip install mothertongueindex   # or: pip install -r requirements.txt

# Your language vs English:
python -m mti "আমি বাংলায় গান গাই, আমি বাংলার গান গাই"

# Explain the cost and the capability impact:
python -m mti --models gpt-4o,gpt-4,sarvam1,claude --why --capability "your text"

# Serve this website with the live analyzer:
python web/server.py    # then open http://localhost:8000

Answers

Frequently asked

Why does my language cost more tokens than English?

Every mainstream tokenizer learned its vocabulary from a mostly-English mixture, so words and characters from other languages split into more, smaller pieces. That is tokenizer fertility. The same meaning in a different language is charged a different number of tokens.

Does this affect reasoning, or only price?

Both. A context window holds a fixed number of tokens, not a fixed amount of meaning. Higher fertility means less of your content fits, which the literature links to weaker in-context learning and reasoning at fixed budget. The tool reports this as derived effective-context loss and ships a probe to measure it.

How can you show a Claude or Gemini count with no public tokenizer?

You cannot exactly, and we do not pretend to. Claude, Gemini, and Grok are shown as clearly-labelled estimates from a per-script heuristic. OpenAI and open-weight models use their real tokenizers, so those are exact.

Is this a cost or pricing calculator?

No. It is an understanding tool. It shows token efficiency and its consequences. It does not track per-model prices, which change often; the xEN ratio tells you the relative cost of your language versus English on the same model, which is the durable insight.

Which languages are supported?

All of them. The engine works from Unicode grapheme clusters and the model's real tokenizer, not a fixed list, so any language in any script can be measured.

How does this relate to Project Bornomala?

MotherTongueIndex is a Bornomala subproject. Bornomala is a Bengali-first language technology programme whose thesis is that the binding constraint is data, not compute. This tool quantifies the tokenizer half of that inequity, and will benchmark the Bornomala Bengali tokenizer once it ships.
